# Build-in-public contribution sprint

The goal is a steady trail of useful, reviewable work. Contributions should improve the project or help another person use it; empty commits and tiny cosmetic changes made only to inflate a count do not help the project earn trust.

## First month

### Week 1 — Make the project understandable

- Publish a clear project overview, local run instructions, and a short demo walkthrough.
- Ask fluent speakers and multilingual AI builders to review the first challenge format.
- Turn concrete feedback into separate issues and focused changes.

### Week 2 — Make the first hunt playable

- Add one non-sensitive, human-reviewed example chosen with fluent reviewers.
- Show the two model responses and ask players to identify what changed or was missed.
- Record the reasoning and reviewer context; do not present one judgment as a universal language score.

### Week 3 — Make contributions easy

- Improve keyboard and mobile use based on a real review.
- Add a contribution guide for proposing a challenge card, including permission, attribution, and privacy checks.
- Make the export format easy for other tools and benchmarks to consume.

### Week 4 — Share what was learned

- Run a small feedback session with speakers and developers.
- Summarize what worked, what did not, and what changed in the project.
- Publish a LinkedIn update with a working demo and one concrete lesson, crediting collaborators who agree to be named.

## Sustainable rhythm

Aim for a few substantive, well-described changes each week, then share a short progress note when there is something real to show. Keep a running changelog of decisions and lessons so future work stays connected. GitHub may not count every activity toward the profile contribution graph, and a higher count cannot be guaranteed.
